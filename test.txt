تو نقش یک Senior Backend QA Engineer + Security Engineer را داری.

هدف: پروژه Backend فعلی را در محیط LOCAL به‌صورت کامل بررسی و تست کن.

تکنولوژی پروژه را از روی کد واقعی تشخیص بده و بر اساس همان کار کن. حدس نزن. قبل از ایجاد یا تغییر هر فایل، ساختار پروژه، package.json، routes، controllers، services، validations، middlewareها، Prisma schema، migrations، مدل‌ها، Redis/BullMQ، authentication و integrationهای خارجی را بررسی کن.

مهم:

* این مرحله فقط برای LOCAL است.
* فعلاً هیچ Load Test سنگینی انجام نده.
* فعلاً به Production یا Staging دست نزن.
* دیتابیس Production را هرگز استفاده نکن.
* منطق فعلی برنامه را بدون دلیل تغییر نده.
* اگر Bug پیدا کردی، ابتدا آن را گزارش کن و فقط در صورت نیاز برای اجرای صحیح تست، حداقل تغییر لازم را انجام بده.
* تست‌ها باید روی رفتار واقعی Backend نوشته شوند، نه رفتار فرضی.
* TypeScript اضافه نکن اگر پروژه JavaScript است.
* از CommonJS استفاده کن اگر پروژه فعلی CommonJS است.
* Secret، password، token یا credential واقعی را داخل تست‌ها commit نکن.

PHASE 4 - AUTHENTICATION
========================

برای endpointهای protected تست کن:

1. request بدون authentication
2. invalid token
3. malformed token
4. expired token اگر قابل تست است
5. modified token

========================================
PHASE 5 - AUTHORIZATION / RBAC
==============================

برای roleهای موجود پروژه تست کن.

مثلاً:

ADMIN
COMPANY
USER
SUPER_ADMIN

البته فقط roleهای واقعی پروژه را استفاده کن.

برای هر endpoint بررسی کن:

* role مجاز
* role غیرمجاز
* user بدون permission
* resource متعلق به user دیگر
* resource متعلق به company دیگر

خصوصاً IDOR را جدی بررسی کن.

سناریو:

User A → Resource A
User B → تلاش برای GET/UPDATE/DELETE Resource A

نباید User B بتواند Resource A را دستکاری یا اطلاعات خصوصی آن را دریافت کند.

همین تست را برای تمام endpointهای دارای resource ID انجام بده.

========================================
PHASE 6 - BUSINESS LOGIC
========================

قوانین Business Logic پروژه را از روی کد استخراج کن و تست کن.

مثلاً:

* وضعیت‌های مجاز resource
* transitionهای وضعیت
* ownership
* lock شدن resource
* duplicate prevention
* date constraints
* dependency constraints
* ordering
* progress rules
* limits
* uniqueness
* state transitions

هرجا rule وجود دارد، حداقل یک تست valid و چند تست invalid داشته باش.

اگر rule فعلی با چیزی که از کد انتظار می‌رود تناقض دارد، آن را به عنوان BUG یا POSSIBLE BUG گزارش کن و خودسرانه تغییر نده.

سناریوی مهم:

برای createMany نیز:

* valid data
* null values

را بررسی کن.

PHASE 8 - SECURITY TESTING
==========================

در LOCAL تست‌های امنیتی کنترل‌شده انجام بده.

موارد:

1. IDOR
2. Broken Access Control
3. Authentication bypass
4. RBAC bypass
5. Mass Assignment
6. SQL Injection
7. NoSQL Injection اگر MongoDB وجود دارد
8. XSS payload handling
9. Path Traversal
10. Prototype Pollution در صورت مرتبط بودن
11. HTTP parameter pollution
12. oversized payload
13. malformed JSON
14. sensitive information disclosure
15. stack trace leakage
16. internal error leakage
17. unsafe dynamic SQL
18. unsafe raw Prisma queries
19. unsafe file paths
20. unrestricted resource access

برای SQL Injection اگر Prisma از raw query استفاده می‌کند، تمام `$queryRaw` و `$queryRawUnsafe` و queryهای dynamic را بررسی کن.

هیچ تست destructive روی سیستم واقعی انجام نده.

========================================
PHASE 12 - ERROR HANDLING
=========================

تمام endpointها را بررسی کن که:

* status code صحیح
* error format یکسان
* stack trace در production-style response لو نرود
* database error مستقیماً به client برنگردد
* internal paths لو نرود
* credentials لو نرود
* SQL query لو نرود

مثلاً مشخص کن کجاها 400، 401، 403، 404، 409، 422، 429 و 500 باید استفاده شوند.

IMPORTANT RULES
===============

1. قبل از تست، کد را بخوان.
2. endpoint جدید فرض نکن.
3. business rule جدید اختراع نکن.

12. هر vulnerability را با reproduction مشخص گزارش کن.
13. اگر قسمتی از پروژه تست‌پذیر نیست، علتش را گزارش کن.
14. اگر تستی به configuration خاص نیاز دارد، configuration موردنیاز را مشخص کن.
15. تمام تغییرات ایجادشده توسط خودت را در پایان فهرست کن.
